## 1. One-paragraph summary

Recaply is a native iOS app that records a meeting or lecture using the microphone (and optionally the camera), transcribes the speech on-device, runs a custom CoreML text classifier to flag action items and decisions inside the transcript, and then calls a cloud LLM (GLM primary, Deepseek fallback) to produce a clean structured summary. The result is an automatic, searchable meeting recap with highlighted action items, no manual note-taking required. It solves a real problem, showcases a layered AI/ML architecture on-device, and its demo needs no external dataset because the user records the test content themselves.

## 4. Decided scope (MVP)

These are the conclusions reached during brainstorming. Treat them as locked unless Ash says otherwise.

1. **Capture: microphone plus camera.** No screen recording in v1. Screen recording on iOS needs a Broadcast Extension (extra target, entitlements, App Group) and adds large compile risk for marginal value to a summarizer. It is listed as a stretch goal only (see section 10).
2. **Transcription: on-device Speech framework.** `SFSpeechRecognizer` converts the recorded audio file into timestamped text. No network needed for transcription.
3. **CoreML: a custom text classifier.** It labels each transcript sentence as one of `action_item`, `decision`, `question`, or `discussion`. This is the chosen CoreML integration because it directly drives the product value (the app surfaces action items and decisions), rather than being a decorative ML feature. Training happens at the iOS lab (see section 7). Sound classification (ESC-50) is the documented fallback if the text dataset proves too much work (see section 10).
4. **Summarization: cloud LLM via API.** GLM is primary (reuse the `GLMService` pattern from FitnessApp), Deepseek is fallback (same OpenAI-compatible request shape). Output is a structured JSON summary (overview, action items, decisions, key points).
5. **Storage: Core Data, local only.** Recordings, transcripts, sentence classifications, and summaries are persisted locally. No Firebase in v1 to minimize SPM and compile risk. Cloud sync is a stretch goal.
6. **UI: SwiftUI, MVVM.** Same View to ViewModel (`@MainActor ObservableObject`) to Service pattern as FitnessApp. Dark theme.

## 5. System architecture

```
+-------------------+   +--------------------+   +-----------------------+
|   Capture layer   |   | Intelligence layer |   |    Persistence layer  |
|  AVFoundation     |-->|  Speech framework  |-->|     Core Data         |
|  - mic (.m4a)     |   |  (audio -> text)   |   |  Recording, Transcript|
|  - camera (.mp4)  |   |  CoreML classifier |   |  SentenceClassification|
|                   |   |  (sentence labels) |   |  Summary              |
+-------------------+   |  GLM/Deepseek API  |   +-----------------------+
                        |  (text -> summary) |              |
                        +--------------------+              |
                                  |                         |
                                  v                         v
                        +--------------------+   +-------------------+
                        |   Presentation     |   |     App layer     |
                        |   SwiftUI MVVM     |<--|  RecaplyApp,      |
                        |   Record, Library, |   |  RootView, Tabs   |
                        |   Detail, Settings |   +-------------------+
                        +--------------------+
```

**End-to-end data flow (a single recording):**

1. User taps Record. `RecordingService` captures microphone via `AVAudioEngine`/`AVAudioRecorder` to an `.m4a` file, and optionally camera via `AVCaptureSession` to an `.mp4` file, both in the app sandbox.
2. User taps Stop. A `Recording` entity is written to Core Data (file URLs, duration, timestamp).
3. `TranscriptionService` runs `SFSpeechRecognizer` on the audio file and produces a timestamped transcript, split into sentence segments. Stored as `Transcript` + `TranscriptSegment`.
4. `ClassificationService` runs the CoreML text classifier on each segment, storing a `SentenceClassification` (label + confidence).
5. `SummarizationService` sends the transcript (with labels) to the GLM API (fallback Deepseek) and stores the returned structured `Summary`.
6. UI: the Library lists recordings. The Detail screen shows the summary (with action items and decisions highlighted), the full transcript with inline classification badges, and audio/video playback.

**Key design rule (isolation):** each service has one job, communicates through value-type models, and is constructor-injected (`.shared` default, overridable for tests). Views never touch AVFoundation, Speech, CoreML, or the network directly.

## 7. CoreML model plan (text classifier)

This is the "Jalur B" custom-model decision, scoped realistically.

- **Task type:** text classification, single-label, multi-class.
- **Classes (4):** `action_item`, `decision`, `question`, `discussion`.
- **Input:** one transcript sentence (string).
- **Output:** predicted label + confidence.
- **Training data:** ~200 to 400 labeled sentences, balanced across the four classes. **Primary approach: AI-generated synthetic data.** Prompt an LLM (GLM, Deepseek, or ChatGPT) to produce varied meeting/lecture sentences per label and export as a `text,label` CSV (for example, "generate 50 action-item sentences, 50 decisions, 50 questions, 50 general discussion"). This is fast and gives a defensible "synthetic data generation" methodology for the report. Fallbacks if quality is poor: hand-label real transcript sentences, or filter a public dialogue-act dataset (AMI Meeting Corpus, HuggingFace). Guidelines: keep roughly equal counts per class, vary phrasing and topics, and mix in a handful of real sentences so the model does not overfit the LLM's style. Note: generating training data with AI is a development resource and does not conflict with the rule that the report text itself must be hand-written.
- **Training location:** the iOS lab Mac, using Create ML's Text Classifier template (roughly 30 minutes). Alternatively, train on Linux with scikit-learn (TF-IDF + LogisticRegression) and convert with `coremltools` if lab time is tight. Ash has confirmed training moves to the lab.
- **Integration:** drop the exported `ActionItemClassifier.mlmodel` into `Resources/Models/`. Wrap it in `ActionItemClassifier.swift` (mirror FitnessApp's `ExerciseClassifierManager`). Provide a graceful fallback (return `discussion` with confidence 0) if the model is missing, so the app still builds and runs before the model exists.
- **Why text over sound:** sound classification (ESC-50) has the easiest data, but its value to a summarizer is peripheral (applause/laughter detection, silence trimming). Text classification is central to the product (it is what surfaces action items), so the CoreML model earns its place rather than being decorative.

### Shared contracts (the collaboration points)

These are the interfaces agents agree on up front and must not break silently. Any change must be recorded in `.agents/SHARED_STATE.md`.

- `Recording` model: `id`, `createdAt`, `audioURL`, `videoURL?`, `duration`.
- `TranscriptSegment` model: `id`, `recordingId`, `index`, `text`, `timestamp`.
- `SentenceClassification` model: `segmentId`, `label` (enum), `confidence`.
- `SummaryPayload` model: `overview`, `actionItems: [String]`, `decisions: [String]`, `keyPoints: [String]`.
- Services are singletons with constructor injection (`.shared` default, overridable) so any agent's code is unit-testable by another.

## 9. Dependencies

Intentionally minimal to keep compile risk low.

- **System frameworks only** for everything except the LLM call: AVFoundation, Speech, Sound Analysis (optional), CoreML, Natural Language (optional), Core Data, SwiftUI.
- **GLM/Deepseek:** plain `URLSession` HTTP, OpenAI-compatible `/v1/chat/completions`. No SDK needed.
- **No Firebase in v1.** No external SPM packages required. This is a deliberate reduction in compile risk versus the NovelDex project (which pinned Firebase 10.29.0). If cloud sync is added later, it becomes a stretch goal.

## 11. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| App does not compile on first lab build (authored on Linux) | High, blocks Demo (20%) and Source (10%) | Make compile verification the very first task at the lab, before any feature polish. Keep dependencies to system frameworks only. |
| Speech framework one-minute task limit and permission prompts | Medium | Implement task-restart logic for long recordings; request `NSSpeechRecognitionUsageDescription` and microphone usage strings in `Info.plist`. |
| Missing or invalid API key crashes the app | Medium | Mirror FitnessApp: store key in Keychain, validate before call, show a friendly empty state in Settings, never force-unwrap. |
| CoreML model not ready before build | Medium | Ship with a stub fallback classifier so the app runs without the model; drop the trained `.mlmodel` in later. |
| Text classifier labels are noisy | Low (acceptable for a class demo) | Keep confidence scores visible; let the user edit labels; document this honestly in the Testing section. |
